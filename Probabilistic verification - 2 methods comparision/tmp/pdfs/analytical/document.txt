The key distinction is this: exact VQE semantics gives a continuous-state stochastic kernel; PRISM/Storm require a finite abstraction. The main research
problem is therefore not writing the property—it is deriving a sound finite transition relation from the measurement and optimizer semantics.

Core construction
An analytical probabilistic VQE model should be built through the following semantic refinement:

VQE operational semantics → concrete stochastic kernel → finite probabilistic abstraction → DTMC/MDP/IDTMC/IMDP → prob

The transition probabilities are not learned from execution frequencies. They are derived from:

  1. the Born-rule distribution of quantum measurements;

  2. the finite-shot estimator;

  3. the optimizer update rule;

  4. the stopping rule;

  5. any explicitly assumed noise, failure, or retry model.

VQE itself combines quantum expectation-value evaluation with classical optimization. Under ideal exact expectation evaluation and a deterministic
optimizer, the process is deterministic. Probability enters through finite-shot measurement, physical noise, randomized optimization, initialization, and
execution failures. (Nature)

7. Select the correct model class

DTMC
Use a DTMC when all execution choices are fixed:

    fixed optimizer;

    fixed shot allocation;

    fixed backend;

    fixed retry policy;

    fixed stopping policy;

    fixed noise model.

The only remaining variation must be probabilistic.

                                                                      D = (S, s0 , P , L).
                                                                                        ​




For your first analytical model, this is the cleanest choice.

MDP
Use an MDP when the execution protocol chooses among actions:

                                                                             at ∈ A(st ),
                                                                               ​            ​




such as:

    low-shot versus high-shot evaluation;

    optimizer selection;

    backend selection;

    retry versus abort;

    continue versus stop;

    conservative versus aggressive update.

PRISM interprets Pmin and Pmax over strategies resolving these nondeterministic choices and can export optimizing strategies. (Prism Model Checker)

IDTMC or IMDP
Use interval models when:

    the abstract state contains multiple concrete parameter values;

    hardware noise is bounded rather than exactly known;

    an analytical approximation produces certified probability bounds;

    backend reliability is only known within an interval.

For an IMDP, PRISM separates quantification over strategies from quantification over probability intervals. For example:

Declared convergence
The implemented stopping rule fires:

for some number of iterations.

Valid convergence
For a benchmark where the reference energy is available:

                                                           ϕvalid = ϕdeclared ∧ ∣E(θt ) − E∗ ∣ ≤ ϵ.

                                                         ϕpremature = ϕdeclared ∧ ∣E(θt ) − E∗ ∣ > ϵ.

For a research evaluation on small Hamiltonians, using a classically known E∗ allows you to verify both declared and valid convergence.

9. Use iteration counters correctly
A property such as

 text

  P=? [ F<=50 "converged" ]


bounds the number of model transitions, not automatically the number of VQE optimizer iterations.

If your model contains separate transitions

                                                      prepare → measure → aggregate → update,

then one VQE iteration may consume four or more model transitions.

For bounded VQE convergence, either:

  1. make one model transition correspond to one complete VQE iteration; or

  2. use an explicit iteration counter:

 text

  P=? [ F ("valid_converged" & iter<=50) ]


The second formulation is safer when the execution model includes retries, failures, and internal phases. PRISM expresses reachability and bounded
temporal properties through its probabilistic temporal-logic property language. (Prism Model Checker)

2. The critical problem with COBYLA
The most important issue is not hardware noise. It is the optimizer.

Your trace currently records:

                                                                            (θt , Et ),

but COBYLA’s next parameter vector is not determined only by this pair. COBYLA maintains an internal interpolation model and trust-region-related state.
Current SciPy documentation describes COBYLA as a linear-approximation method, and also notes that an optimizer iteration can require multiple objective-
function evaluations. (SciPy Documentation)

Consequently:

is not well-defined for your existing implementation.

Two executions can reach the same θt and obtain the same current energy but have different future proposals because their earlier objective observations

produced different internal COBYLA states.

counts calls to cost_func , which are objective-function evaluations. It does not necessarily count complete optimizer iterations. SciPy explicitly
distinguishes iterations from function evaluations. (SciPy Documentation)

14. Final model assumptions
Your paper should state these explicitly.

A1: Fixed VQE instance
The Hamiltonian, ansatz structure, parameter ordering, measurement grouping, shot allocation, optimizer, initial parameters, and iteration bound are fixed.

A2: Logical circuit semantics
The quantum state is generated by exact unitary execution of the logical ansatz.

A3: Born-rule randomness only
The only probabilistic source is finite-shot projective measurement.

A4: Independent executions
Shots are independent and identically distributed within each measurement group, and separately executed groups and candidates are independent.

A5: No physical noise
Gate noise, readout noise, drift, crosstalk, job failure, and queue behavior are excluded.

A6: Exact classical processing
Measurement counts are converted to Pauli expectations and energies without arithmetic or parsing errors.

A7: Finite parameter space
All optimizer parameters lie on a fixed periodic grid.

A8: Explicit optimizer
The optimizer evaluates a fixed candidate set, follows a fixed coordinate schedule, and uses deterministic tie-breaking.

A9: One transition per update
One DTMC transition represents one complete optimizer update, not one circuit execution or objective-function call.
